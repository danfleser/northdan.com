Ce este gRPC (gRPC Remote Procedure Calls)?

Framework open-source prin care un serviciu apelează funcțiile altui serviciu ca pe unele locale — folosit mai ales între microservicii și între aplicațiile mobile și server.

gRPC este un framework open-source de apel de procedură la distanță (RPC, Remote Procedure Call), lansat de Google în 2015, prin care un program apelează o funcție aflată pe alt server ca pe una locală, cu mesaje Protocol Buffers transmise peste HTTP/2. Numele nu înseamnă „Google RPC”: FAQ-ul oficial grpc.io îl explică drept „gRPC Remote Procedure Calls”, iar litera g primește alt sens la fiecare versiune (1.1 „good”, 1.2 „green”). Google a folosit mai bine de un deceniu un sistem intern numit Stubby, care lega microserviciile din centrele sale de date, dar Stubby nu se baza pe niciun standard și era legat de infrastructura Google. În martie 2015, odată cu apariția SPDY, HTTP/2 și QUIC, Google a hotărât să construiască următoarea versiune ca proiect open-source. gRPC 1.0 a apărut în august 2016, iar proiectul a fost acceptat în Cloud Native Computing Foundation (CNCF) la 16 februarie 2017. Licența este Apache 2.0.

În loc de mesaje text, serviciile schimbă mesaje binare compacte, cu structura definită strict în avans într-un fișier .proto. Protocol Buffers sunt, potrivit documentației oficiale, ca JSON-ul, dar mai mici și mai rapide. gRPC nu înlocuiește REST către publicul larg, pentru că browserele nu îl vorbesc nativ, ci se potrivește între serviciile tale interne: microservicii care schimbă volume mari de date, sisteme unde fiecare milisecundă contează. Pentru firma ta înseamnă mai puțin trafic și costuri mai mici la apelurile interne dese, plus erori de integrare prinse înainte de producție, nu de clienți. Verificat la 18 noiembrie 2026 pe grpc.io.

De ce contează pentru afacerea ta

Viteză la trafic intern mare

Mesajele binare compacte și conexiunile HTTP/2 reduc semnificativ latența și volumul de date între servicii — economie directă la infrastructură când volumele cresc.

Contract strict, erori prinse devreme

Structura mesajelor e definită formal în fișiere .proto: dacă două servicii nu se mai potrivesc, eroarea apare la compilare în limbajele compilate (Java, Go, C#), nu într-un incident de producție.

Servicii în limbaje diferite, fără fricțiune

Din același contract se generează automat cod pentru Java, Go, Python, C# și altele — echipele pot alege limbajul potrivit fără să complice integrarea.

Cum funcționează gRPC

Totul pornește de la un fișier .proto, în care descrii serviciul, metodele care pot fi apelate de la distanță și mesajele pe care le primesc și le întorc. Compilatorul protoc, cu pluginul gRPC, generează din acest fișier interfața serverului și un stub pentru client. Serverul implementează metodele; clientul apelează stub-ul ca pe un obiect local, iar stub-ul împachetează parametrii, trimite cererea și întoarce răspunsul. Transportul este HTTP/2, deci mai multe apeluri circulă pe aceeași conexiune.

Documentația oficială definește patru tipuri de metode. Unary: clientul trimite o cerere și primește un răspuns, ca la un apel obișnuit de funcție. Server streaming: clientul trimite o cerere și citește un flux de mesaje. Client streaming: clientul scrie un flux de mesaje, iar serverul răspunde la final. Bidirectional streaming: ambele părți trimit mesaje pe fluxuri independente, iar ordinea mesajelor se păstrează în fiecare flux. Clientul poate fixa și un termen limită (deadline): dacă serverul nu răspunde la timp, apelul se încheie cu eroarea DEADLINE_EXCEEDED.

Exemplu: un serviciu descris în .proto

Exemplul din introducerea oficială grpc.io arată un serviciu de salut. Serviciul Greeter are o metodă: rpc SayHello (HelloRequest) returns (HelloReply). Mesajul HelloRequest conține un câmp: string name = 1. Mesajul HelloReply conține un câmp: string message = 1. Cifra 1 este numărul câmpului în format binar, nu o valoare.

Din aceste câteva rânduri se generează cod pentru client și server, în limbajul fiecărei echipe. Documentația oficială listează, printre altele, C#/.NET, C++, Dart, Go, Java, Kotlin, Node, Objective-C, PHP, Python, Ruby, Rust și Swift. Poți avea un server în Java și clienți în Go, Python sau Ruby. De aceea fișierul .proto merită cerut la orice predare a unui sistem cu microservicii: este descrierea unică și verificabilă a interfeței.

gRPC vs REST

Transport: gRPC cere HTTP/2; REST este un stil de arhitectură, de obicei peste HTTP/1.1 sau HTTP/2. Format: gRPC folosește implicit Protocol Buffers binar și poate lucra și cu JSON; REST folosește de regulă JSON text. Contract: la gRPC fișierul .proto este obligatoriu; la REST descrierea (de exemplu OpenAPI) este opțională. Streaming: pe lângă apelul unary, gRPC are trei moduri de streaming (server, client, bidirecțional); REST este cerere–răspuns, iar pentru mesaje trimise de server are nevoie de WebSocket sau alt mecanism. Erori: gRPC are propriile coduri de stare, nu codurile HTTP. Browser: REST merge direct; gRPC are nevoie de gRPC-Web și de un proxy, implicit Envoy, pentru că niciun API din browser nu oferă controlul fin al cererilor cerut de HTTP/2.

Regula practică: REST la marginea sistemului, pentru API-uri publice și integrări cu parteneri, și gRPC în interior, între servicii. Pentru o a treia variantă, GraphQL este un limbaj de interogare prin care clientul alege forma răspunsului; are propria pagină în dicționar.

Când are sens gRPC pentru o firmă și când nu

Pagina oficială grpc.io indică patru scenarii principale: sisteme distribuite cu latență mică și scalabilitate mare, aplicații mobile care comunică cu un server în cloud, protocoale noi care trebuie să fie precise, eficiente și independente de limbaj, și un design în straturi care permite extensii precum autentificare, load balancing, logging și monitorizare. Printre utilizatorii numiți pe site sunt Square, Netflix, CoreOS, Docker, CockroachDB, Cisco și Juniper Networks.

Nu are sens, de regulă, pentru un sistem mic, cu câteva servicii, pentru un API public sau de parteneri ori pentru un site al cărui front-end apelează direct serverul. În aceste cazuri REST rămâne mai simplu și se testează cu unelte obișnuite.

Întrebări frecvente

Ce înseamnă gRPC?⌄

gRPC înseamnă „gRPC Remote Procedure Calls”, un acronim recursiv, potrivit FAQ-ului oficial grpc.io. Nu înseamnă „Google RPC”, deși l-a creat Google. În română, RPC se traduce prin apel de procedură la distanță: un program cheamă o funcție de pe alt server.

Când alegem gRPC și când REST?⌄

REST pentru API-uri publice și integrări cu parteneri (universal înțeles, ușor de testat), gRPC pentru comunicarea internă dintre microservicii, unde volumul și latența contează. Arhitecturile mature le combină exact pe acest criteriu.

Care e diferența dintre RPC și gRPC?⌄

RPC este ideea generală de a apela o funcție aflată pe alt calculator ca pe una locală. gRPC este un framework concret de RPC, creat de Google, care adaugă transport HTTP/2, mesaje Protocol Buffers, cod generat automat pentru mai multe limbaje și streaming.

Poate un browser să vorbească direct gRPC?⌄

Nu nativ: browserele nu oferă controlul asupra cererilor cerut de protocol. Soluția este gRPC-Web, disponibil general (GA), care trece prin proxy, implicit Envoy, sau un gateway care traduce în HTTP clasic. De aceea gRPC rămâne o tehnologie de interior.

Ce sunt Protocol Buffers (protobuf)?⌄

Formatul binar de serializare pe care gRPC îl folosește implicit: datele se descriu o dată într-un fișier .proto, apoi se codifică compact. Documentația protobuf.dev îl descrie ca pe JSON, dar mai mic și mai rapid.

Este gRPC mai rapid decât REST?⌄

De regulă da, la trafic intern intens, pentru că mesajele binare sunt mai mici și HTTP/2 permite mai multe apeluri pe aceeași conexiune. Nu există un factor universal: diferența depinde de mărimea mesajelor, de rețea și de implementare, deci se măsoară pe cazul tău.
