Ce este OpenAPI (OpenAPI Specification) și la ce folosește

Formatul standard, în YAML sau JSON, în care se descrie complet un API: ce adrese are, ce parametri primește și ce răspunsuri întoarce.

7
secțiuni
5
întrebări cu răspuns

OpenAPI (OpenAPI Specification, OAS; până în 2016 Swagger Specification) este standardul deschis prin care un API HTTP se descrie complet într-un singur fișier YAML sau JSON — adrese, metode, parametri, răspunsuri, erori și autentificare — astfel încât oamenii și programele să-l poată folosi fără acces la codul sursă. Din acest fișier se generează automat documentație interactivă, cod de client în zeci de limbaje și teste care verifică dacă API-ul își respectă propriul contract.

Ca la planurile unui arhitect, fiecare cotă e desenată, nu povestită. Diferența practică e mare: o integrare cu un API documentat OpenAPI începe în ore — partenerul citește specificația și generează codul de legătură; una cu un API descris «prin emailuri» începe cu săptămâni de întrebări. Pentru firma ta, regula e simplă: dacă plătești construcția unui API, cere specificația OpenAPI ca livrabil obligatoriu în contract — e garanția că integrările viitoare și o eventuală schimbare de furnizor nu pornesc de la zero. Verificat la 18 noiembrie 2026 pe spec.openapis.org: cea mai nouă versiune este 3.2.1, publicată la 10 septembrie 2026.

Termenul te interesează pentru un proiect concret? Documentăm și construim API-uri cu specificații OpenAPI — vezi serviciul de integrare API

De ce contează pentru afacerea ta

✓Integrări care pornesc în ore, nu săptămâni

Partenerii primesc o specificație completă și își generează singuri codul de legătură — dispar lunile de emailuri cu «dar câmpul acesta ce format are?».

✓Documentație care nu minte niciodată

Documentația interactivă se generează din aceeași specificație pe care rulează API-ul — nu mai există PDF-uri rămase în urmă cu trei versiuni față de realitate.

✓Contract verificabil automat

Testele compară permanent comportamentul real al API-ului cu specificația — orice abatere se prinde înainte de livrare, nu în producția partenerilor.

Ce conține un fișier OpenAPI

Fișierul are câmpuri de nivel superior fixe: «openapi» (versiunea specificației folosite), «info» (titlul și versiunea API-ului), «servers» (adresele de bază), «paths» (adresele din API și operațiile de pe ele), «components» (scheme, răspunsuri și mecanisme de securitate reutilizabile) și «security» (cum se autentifică un apelant). De exemplu, o operație POST /facturi poate avea schema cererii definită o singură dată în «components» și refolosită oriunde apare.

YAML și JSON descriu același obiect; dacă folosești YAML, versiunea recomandată e 1.2, iar fișierul de intrare se numește de preferință «openapi.json» sau «openapi.yaml» (OAS 3.2.1, §3.1 și §4.1). O greșeală frecventă: câmpul «openapi» e versiunea specificației (de exemplu 3.1.1), nu versiunea API-ului tău; aceea se trece în «info.version».

OpenAPI vs Swagger

OpenAPI este specificația, condusă de OpenAPI Initiative, un proiect open source al Linux Foundation, format în noiembrie 2015 de SmartBear, 3Scale, Apigee, Capital One, Google, IBM, Intuit, Microsoft, PayPal și Restlet. Swagger este numele inițial al specificației (Swagger 1.0 din 10.08.2011, Swagger 2.0 din 08.09.2014) și, astăzi, marca uneltelor SmartBear: Swagger UI, Swagger Editor, Swagger Codegen, SwaggerHub.

Swagger 2.0 a fost donat la 31.12.2015, iar prima versiune sub noul nume, OpenAPI 3.0.0, a apărut la 26.07.2017. Deci «Swagger 2.0» și «OpenAPI 3.x» înseamnă generația veche, respectiv generația nouă a aceleiași specificații. Swagger UI este open source, sub licența Apache-2.0.

OpenAPI vs API REST

REST este un stil de arhitectură pentru construirea unui API; OpenAPI este un format de descriere. Un API REST poate exista fără fișier OpenAPI, iar OpenAPI poate descrie API-uri HTTP care nu respectă strict REST — specificația vorbește despre «interfețe HTTP», nu doar REST. Nu acoperă GraphQL (are propriul limbaj de scheme), gRPC (folosește Protocol Buffers) și nici API-urile bazate pe evenimente sau mesaje, descrise cu AsyncAPI.

Alte sensuri: Open API și Openapi

În vorbirea curentă, «open API» înseamnă un API deschis altor firme, nu doar uz intern, de exemplu API-urile de open banking, deschise furnizorilor autorizați — nu specificația. «Openapi» (openapi.ro) este un serviciu comercial românesc care vinde API-uri de date de firmă: date după CIF, cursul BNR, validarea CIF, CNP și IBAN. Are același nume, dar nu are legătură cu standardul.

Versiunile OpenAPI (verificat la 18.11.2026)

Din tabelul de revizuiri al specificației (spec.openapis.org): 3.0.0 din 26.07.2017 (ultima corecție, 3.0.4, din 24.10.2024); 3.1.0 din 15.02.2021, unde obiectul Schema devine un superset al JSON Schema Draft 2020-12 și apare câmpul «webhooks» (ultima corecție, 3.1.2, din 19.09.2025); 3.2.0 din 19.09.2025, cu etichete imbricate (parent, kind), tipuri media pentru streaming, «additionalOperations» pentru alte metode HTTP și «querystring»; 3.2.1 din 10.09.2026, cea mai nouă.

Recomandarea noastră pentru un contract: cere cel puțin 3.1; cere 3.2 când uneltele din lanțul furnizorului o validează. Swagger UI, de pildă, a adăugat «suport de bază pentru OpenAPI 3.2.0» abia în versiunea 5.32.0, din 27.02.2026. Versiunea 2.0 rămâne acceptabilă doar la sisteme vechi, cu un plan de conversie.

Întrebări frecvente

OpenAPI și Swagger sunt același lucru?

Aceeași specificație, redenumită: Swagger 2.0 a fost donat la 31.12.2015, iar versiunea următoare a apărut în 2017 ca OpenAPI 3.0.0. Astăzi «Swagger» este marca uneltelor SmartBear din jurul ei — Swagger UI pentru documentație interactivă, Swagger Editor pentru scris specificații.

Ce versiune de OpenAPI ar trebui să cer în 2026?

Cere cel puțin 3.1. Cea mai nouă versiune este 3.2.1 (10.09.2026), dar cere 3.2 doar dacă uneltele furnizorului o suportă — Swagger UI are suport de bază din 27.02.2026. Versiunea 2.0 e veche și are sens doar la sisteme existente, cu plan de conversie.

OpenAPI se scrie în YAML sau în JSON?

În oricare, pentru că ambele descriu același obiect. Dacă folosești YAML, specificația recomandă versiunea 1.2, ca fișierul să se poată converti fără pierderi în JSON; fișierul de intrare se numește de preferință openapi.yaml sau openapi.json. Alege formatul pe care îl citește comod echipa, nu unul impus de unealtă.

Specificația OpenAPI se scrie manual?

Ambele abordări există. «Design-first»: specificația se scrie întâi, iar codul o urmează — ideal când mai multe echipe depind de contract. Sau generată din adnotările din cod, mai comodă la proiecte mici. Important e ca ea să existe și să fie sursa de adevăr.

Care e diferența dintre un API și OpenAPI?

API-ul este interfața pe care o expune programul tău; OpenAPI este descrierea standard a acelei interfețe. Un API funcționează și fără ea, dar fiecare integrare pornește atunci din presupuneri, nu dintr-un contract pe care îl poate citi și o unealtă.
