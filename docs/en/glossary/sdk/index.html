What is an SDK?

Software Development Kit: the official bundle of tools, libraries and documentation for building software on a platform or service.

6

6
questions answered

SDK stands for Software Development Kit: the package a platform or service provider gives developers — code libraries, documentation, examples and tools — so they can build apps for that platform quickly and correctly. The examples touch business projects directly: mobile apps are built with Apple's and Google's SDKs; payment flows arrive as processor SDKs (Stripe, for one) that bundle ready-made card forms and validation rather than leaving developers to assemble raw API calls; login with Google, maps, push notifications and analytics all snap in the same way. The classic confusion is the API relationship: the API is the communication contract (what you can ask a service), the SDK its comfortable implementation in a given language — an API can be used without one, but the official kit saves time and mistakes, which is why "do they offer an SDK for our stack?" quietly decides what an integration costs. The angle buyers rarely hear: every third-party SDK mounted in your app is foreign code running with your app's permissions. Analytics and advertising kits have historically been the channel through which otherwise honest apps leaked user data — with the privacy liability landing on the app's owner, meaning you — and outdated kits carry known vulnerabilities. Two legitimate acceptance questions follow: which third-party SDKs does our app contain, with a reason for each; and who keeps them current, since platforms update constantly and app stores eventually reject antique versions.

Why it matters for your business

✓Integrations in days, not months

The SDKs' ready-built components — payments, maps, authentication — compress exactly the integration work that would otherwise be written and tested from zero.

✓Edge cases handled by the vendor

The official SDK implements the platform's edge cases and security requirements — fewer errors than any artisanal reimplementation.

✓Updates in step with the platform

When the processor changes its payment flow or Apple changes the rules, the updated SDK carries the compliance — an upgrade effort, not a rebuild.

What an SDK contains

An SDK usually has four parts: code libraries (often including the client for the service's API), documentation and guides, code samples, and working tools such as a compiler or build tools, a debugger and an emulator.

The Android SDK, for example, is composed of multiple packages, installed and updated through the SDK Manager in Android Studio or the sdkmanager command; the Platform Tools package includes adb (manages an emulator or a device and installs an APK) and fastboot. The SDK for iOS ships inside Xcode. A service SDK, for payments or login, is usually much smaller: a library and its documentation.

SDK vs API, library and framework

The API is the contract: which requests a service accepts and what it answers. The SDK packages one or more APIs for a given language and adds tools. You can use an API without an SDK, but an SDK always has an API underneath.

A code library is code you call; a framework is the structure that calls your code. An SDK can contain libraries and sometimes a framework, besides documentation and tools.

SDK examples from a real project

Platform SDKs: the Android SDK, the iOS SDK in Xcode, the .NET SDK and the JDK (Java Development Kit, the SDK for Java). Service SDKs: Stripe for payments, Firebase for notifications, analytics and crash reports, Google Sign-In and Facebook Login for authentication, OneSignal for push. In AI there is, for instance, the OpenAI Agents SDK.

Many are very common: Apple's list of commonly used SDKs in App Store apps includes FirebaseCore, FirebaseMessaging, FirebaseCrashlytics, GoogleSignIn, FBSDKCoreKit and OneSignal, plus Flutter, Capacitor and Cordova. Your mobile app will typically hold a few platform SDKs and more service SDKs, and each one needs a reason to be there.

Third-party SDKs in your app: what Google Play and Apple require

Google Play: if you include an SDK in your app, you are responsible for making sure the third-party practices and code comply with the Google Play policies, and any data an SDK collects must be treated as if you collected it directly. New releases that use a non-compliant SDK version can be rejected. For a version with critical issues, a temporary release is allowed, then you must update within 90 days or stop releasing with it. The Google Play SDK Index helps you decide whether to adopt, keep or remove an SDK.

Apple: when you use a third-party SDK, you are responsible for all the code the SDK includes in your app. For SDKs on Apple's list, new apps or updates that add them need a privacy manifest and, for binary dependencies, a signature.

Minimum versions have dates. Since 28 April 2026, Apple accepts only apps built with Xcode 26 or later using the SDK for iOS 26. Since 31 August 2026, Google Play requires new apps and updates to target Android 16 (API 36); existing apps must target at least Android 15 (API 35) to stay available to new users on newer Android versions.

At acceptance, the two questions stay: which third-party SDKs does the app contain, and who keeps them current.

Frequently asked questions

API versus SDK — the short version?

The API is the contract: what requests a service accepts and what it answers; the SDK is the kit that makes it convenient in a concrete language — libraries, examples, tools. Every SDK uses an API underneath; not every API has an SDK for every language. When scoping an integration, an official SDK for your technology lowers time and risk — ask early.

Why does it matter which third-party SDKs are inside our company's app?

Because they run with your app's permissions and under your name: analytics and ad SDKs can collect user data (the privacy liability is yours, not the SDK maker's), outdated ones carry published vulnerabilities, and each adds weight and failure points. Buyer's hygiene: an SDK inventory with justification at delivery, minimalism, and updates included in maintenance.

Our older app uses outdated SDKs — what is the real risk?

Three concrete risks: store rejection (for example, since 28 April 2026 Apple accepts only apps built with Xcode 26 and the iOS 26 SDK, and since 31 August 2026 Google Play requires Android 16 / API 36 on updates), published vulnerabilities left open, and features silently degrading on new phones. SDK updates are normal maintenance: cheap done rhythmically, expensive under a deadline.

What does SDK mean in an app?

In an app, an SDK is a ready-made block from another company (payments, login, analytics, push notifications, ads) built into your app's code. It runs with your app's permissions, and the stores hold you responsible for what it collects: Google Play treats an SDK's data collection as yours, and Apple makes you answerable for all the code it brings.

What is the Android SDK?

The Android SDK is Google's set of packages for building Android apps: build tools, Platform Tools (adb, fastboot) and platform versions. It is installed through the SDK Manager in Android Studio. An app's target SDK is the Android version it declares, and Google Play requires that version to be recent.

SDK vs JDK — what is the difference?

The JDK (Java Development Kit) is one specific SDK: the kit for writing and compiling Java programs. "SDK" is the general term for any development kit of a platform or service. An Android project in Java or Kotlin needs a JDK configured for the build, alongside the Android SDK.
