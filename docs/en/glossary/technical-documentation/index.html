Software technical documentation: types and handover

The set of documents describing how a software application is built, installed and repaired, so another team can take it over without its author.

6
sections
7
questions answered

Technical documentation of a software application is the set of documents that describe how the system is built, how it is installed and how it is repaired: the architecture, the API reference (usually an OpenAPI file), the installation README, the operating runbook and the log of architecture decisions (ADRs). It is written for whoever takes the system over — a new developer, another supplier, an auditor — not for the end user.

What happens to your application the week the developer who built it stops answering the phone? Without documentation, the knowledge sits in one head and every change goes through the same person or supplier, at their price. With it, you can change supplier, hire someone else and audit what you bought. It is what makes a competitive re-tender possible and turns a 2 a.m. incident into a procedure. That is why, at handover, the documentation matters as much as the application: specify it in the contract, with acceptance criteria.

Why it matters for your business

✓Independence from people and suppliers

A documented system can be handed to another team without archaeology, which keeps your supplier relationship a choice rather than a dependency.

✓Cheaper, faster maintenance

Developers who can read how the system works spend their hours changing it instead of rediscovering it at your hourly rate.

✓Cover during audits and incidents

Data flows, retention rules and recovery procedures on paper answer auditors quickly and shorten outages.

Types of technical documentation

The architecture answers "what is it made of and how do the pieces talk": components, integrations and where the data lives. Diagrams usually follow Simon Brown's C4 model, with four levels — context, containers, components, code; for a client the first two are enough.

The API reference describes which requests the system accepts and what it returns. It is usually an OpenAPI file (the current version of the specification is 3.2.1, published on 10 September 2026), from which interactive documentation and client code are generated; a new integration starts from it.

The README says how to start the project locally, how to run the tests and which environment variables it needs — where the secrets live, not their values. The runbook collects the operating procedures: backup and restore, restart, what to do about the errors that happen often.

An ADR (Architecture Decision Record) is one page per decision, in the format Michael Nygard proposed in 2011: title, context, decision, status, consequences. It answers "why is it built this way", the question code cannot answer. Add the database schema and the inventory of environments, servers and third-party accounts.

To organise the whole set, the Diátaxis framework splits documentation into four kinds: tutorials, how-to guides, technical reference (the API reference belongs here) and explanation. The end-user manual is a separate set.

What you should receive at handover

For the documentation part, six items fit in a contract annex: an architecture diagram with components and their dependencies; the API specifications; the build and deployment procedure; an inventory of environments, servers and third-party accounts; the data model; an operations runbook for backup, restore and known failure modes.

The acceptance test is simple: someone outside the team installs the system from scratch using only the README and the runbook. Whatever they cannot do from the documents is missing from the documentation. The full handover list — access, accounts, acceptance record — is on the page about what you receive at software project handover.

Technical documentation, user manual, specification

The specification comes before the build and says what the application must do. Technical documentation comes after and says how it is built and operated, for whoever maintains it. The user manual explains how an employee uses it, step by step, with no detail about code or servers.

When technical documentation is a legal duty: the CRA

Regulation (EU) 2024/2847, the Cyber Resilience Act (CRA), requires the manufacturer of a product with digital elements placed on the EU market to draw up technical documentation before placing it on the market and keep it updated at least for the support period (Article 31(1)–(2)). The minimum content is in Annex VII: a description of the system architecture, the software bill of materials (SBOM), the vulnerability disclosure policy, the cybersecurity risk assessment, test reports. The documentation is kept available to authorities for at least 10 years or the rest of the support period, whichever is longer (Article 13(13)).

The main obligations apply from 11 December 2027; vulnerability reporting (Article 14) from 11 September 2026 (Article 71). The regulation concerns firms that sell or distribute software as a product on the EU market; pure SaaS services are outside it; an application built to order for internal use does not fall under it automatically, and its documentation is requested through the contract. Checked on 18 November 2026 against the regulation text on EUR-Lex.

Frequently asked questions

What is the minimum documentation a delivered software project must include?

Six items, and they fit in a contract annex: an architecture diagram with components and their dependencies; interface and API specifications; the build and deployment procedure; an inventory of environments, servers and third-party accounts; the data model; and an operations runbook covering backup, restore and known failure modes. Anything beyond that is welcome but negotiable.

The supplier says the code documents itself — is that acceptable?

Partly true and mostly evasive. Well-written code does explain what a function does, but it never explains why an architecture was chosen, which external systems must be reachable, how to restore a database, or what the third-party contracts are. Those live outside the code by definition. Accept self-documenting code as a reason to skip function comments, never as a reason to skip handover material.

How do we keep documentation current after launch?

Keep it in the same repository as the code and make updating it part of the change itself, so a modification without its documentation update simply is not finished. Then review the small set of critical documents — architecture, runbook, environment inventory — once a quarter. Documentation kept in a separate drive folder goes stale quickly.

What is an ADR (Architecture Decision Record)?

An ADR is a short page per architecture decision: title, context, decision, status and consequences, a format proposed by Michael Nygard in 2011. Kept in the same repository as the code, it shows years later why a solution was chosen and which alternatives were ruled out.

What is a runbook?

A runbook is the set of written procedures for operating the system: how to back up and restore, how to restart services, what to check and what to do about known incidents. It is written so an administrator who did not build the system can follow the steps, even at night, under pressure.

Is technical documentation required by law?

For software delivered as a product (installed at the client, a downloadable application, firmware) on the EU market, yes, from 11 December 2027, under Regulation (EU) 2024/2847, Article 31 and Annex VII; products offered free of charge in the course of a commercial activity count too. A pure SaaS service does not fall under the CRA. For an application built to order for internal use, the duty comes from the contract, so write it in with acceptance criteria.

What is the difference between technical documentation and a user manual?

Technical documentation is for the people who maintain the system (developers, administrators, auditors) and explains architecture, installation and recovery. A user manual is for the people who use it and explains the steps in the interface, without implementation detail.
