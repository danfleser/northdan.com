Dezvoltare aplicații React Native pentru iOS și Android

Prima alegere când firma are deja un produs și o echipă React. Slabă ca prim pas mobil pentru cine nu are nimic construit pe web.

Prima întrebare la un proiect React Native nu e despre aplicație, ci despre inventar: ce rulează astăzi pe React în firma voastră, cine îl întreține și cât din logica aceea se poate refolosi. Răspunsul decide dacă tehnologia e o economie reală sau doar o preferință de echipă.

Când există deja un portal de client, un panou de administrare sau un magazin pe React, aplicația mobilă pornește de la validări, apeluri către server și reguli de business scrise și testate, iar oamenii care le-au scris rămân aceiași. Când nu există nimic pe web, avantajul dispare, iar comparația corectă se face cu Flutter.

Ce se partajează efectiv e logica, nu ecranele: interfața se reconstruiește pe tipare mobile, fiindcă un tabel confortabil pe desktop e inutilizabil pe un telefon ținut într-o mână.

Ce primești

Logica scrisă o singură dată

Validările, apelurile către server și regulile de business din produsul web se refolosesc în aplicație, în loc să fie rescrise pentru fiecare platformă.

Aceiași oameni pe ambele fronturi

Un dezvoltator React devine productiv pe mobil în câteva săptămâni: același limbaj, același model de componente, alt set de ecrane și de gesturi.

Funcțiile de sistem, prin module native

Camera, notificările, cititorul de coduri și plățile în aplicație intră prin module native întreținute public, nu prin soluții improvizate pe proiect.

Predarea nu are surprize

Primiți codul, documentația de construcție, cheile de semnare și conturile de magazin pe firma voastră; orice echipă React poate prelua proiectul.

Pentru ce alegem React Native

Trei forme în care React Native e alegerea evidentă. Geamănul mobil al unui portal de client: aceleași conturi, aceleași reguli de acces, ecrane refăcute pentru telefon. Aplicația internă peste un backend care există deja, folosită zilnic de oameni din depozit sau din teren. Și produsul care trăiește simultan pe web și pe mobil, unde o regulă schimbată trebuie să se aplice în aceeași zi în ambele locuri.

Ce livrăm efectiv pe React Native

Nu avem un produs public al nostru pe React Native; tehnologia o folosim în proiecte de client, iar la cerere deschidem codul și arhitectura într-o discuție tehnică. Distincția între ce se mută și ce se reface o punem pe hârtie în prima săptămână, fișier cu fișier, fiindcă de ea depinde estimarea. În livrare intră aplicația pentru ambele magazine, modulele native fixate pe versiuni verificate, lanțul de construcție reproductibil pe alt calculator și publicarea în cele două magazine.

Compromisurile reale

Fereastra de suport e scurtă. O aplicație lăsată nesupravegheată un an și jumătate ajunge pe o versiune fără corecții, iar recuperarea trece prin dependențele native, nu doar prin cod propriu. Se adaugă cerințele de lanț de build: documentația de suport a proiectului arată că versiunea 0.87 cere minimum Xcode 26, JDK 17 și Android 7.0. Prețul nu vine din React Native, ci din numărul de ecrane, de integrări și de roluri.

Când NU alegem React Native — și ce alegem în loc

Fără moștenire React, argumentul principal dispare și propunem Flutter, care oferă un set de componente mai omogen pe ambele platforme. Când hardware-ul e miezul produsului — scanere industriale, Bluetooth pe utilaje, procesare video — mergem nativ, pe Kotlin sau Swift. Iar când utilizatorul intră rar și instalarea nu se justifică, propunem un PWA sau o aplicație web.

Cine o întreține după ce plecăm noi

Politica de suport React Native, publicată de grupul de lucru pentru release-uri în depozitul reactwg/react-native-releases, întreține ultima versiune minoră și cele două anterioare; restul trec în starea Unsupported, unde nu mai apar versiuni noi, iar recomandarea oficială este migrarea cât mai rapidă.

Consecința practică e un ritm: alinierea la versiune se planifică drept mentenanță, nu ca proiect separat. Regula de buget pe care o folosim pentru software la comandă este de 15–20% pe an din costul dezvoltării, iar în ea intră și aceste alinieri.

Întrebări frecvente

Când NU merită React Native?⌄

Nu merită când echipa React din firmă e formată dintr-un singur om. Codul partajat înseamnă și responsabilitate partajată; cu o singură persoană care înțelege produsul, riscul de indisponibilitate crește pe ambele fronturi deodată.

Cât costă o aplicație în React Native?⌄

Stiva nu fixează bugetul, scopul îl fixează: câte ecrane se desenează, cu ce sisteme vorbește aplicația, câte tipuri de utilizator există și dacă trebuie să meargă fără semnal. Cât din logica web se refolosește scurtează proiectul, dar nu îl transformă. Cifrele orientative stau în ghidul nostru de costuri pentru aplicații mobile.

Găsim ușor programatori React Native în România?⌄

Bazinul e practic bazinul React, deci recrutarea e mai simplă decât pe stive mobile dedicate. Capcana stă în altă parte: experiența pe web nu acoperă automat lanțul de construcție, semnarea și modulele native, iar acolo se pierde timpul la preluarea unui proiect. Măsurători de piață nu publicăm.

Ce se întâmplă la actualizările majore?⌄

Le tratăm ca lucrare planificată de mentenanță, la interval fix, tocmai fiindcă versiunile vechi ies din suport. Un salt peste mai multe versiuni atinge și modulele native, deci costă mai mult decât trei alinieri mici făcute la timp.

Ce primim la predare și pe ce conturi se publică?⌄

Predăm codul sursă, documentația de construcție, cheile de semnare și lista modulelor native cu versiunile lor. Conturile App Store Connect și Google Play Console stau pe firma voastră, deci încasările, recenziile și fișele de magazin nu depind de noi.
